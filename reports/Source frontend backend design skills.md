# Three skills expose Wake Mate's alarm, schema and UI gaps

The three skills ask for different disciplines, and each finds a different weak point in Wake Mate. The biggest defects are in the alarm and the matching backend, not in syntax. `zizi-skills:source-driven-development` demands that framework code be verified against the installed package and official docs. Against expo-notifications 58.1.8, that check shows the daily trigger defaults to `delivery: 'bestEffort'`, which OEM battery policies can defer by minutes. The app also never asks for exact-alarm permission and declares both `SCHEDULE_EXACT_ALARM` and the Play-restricted `USE_EXACT_ALARM`. `backend-design:design` requires six answers (context, data, failures, authorization, idempotence, observability) before code. Applied to `supabase/schema.sql`, they expose fourteen defects. Six are high impact: no daily re-enrolment, exact-minute pairing that makes cold start hopeless, users holding several slots, paired users who cannot leave, block/report that leaves the match untouched, and an unbounded `mark_awake`. `zizi-skills:frontend` is a Vue/Tabler web skill, but its core gates transfer: loading, empty and error states, and proof that the UI is usable. They expose a **1.66:1 contrast failure** on the "Turn alarm off" button, swallowed errors, a deprecated `SafeAreaView`, and no accessibility semantics. The backend fixes were tested on stock PostgreSQL 16, not on real Supabase. The frontend and alarm fixes are unrun static findings, and the Play policy text was never retrieved. The patch is `backend_design_patch_v2.sql` in the notes folder (245 lines, applies on top of `schema.sql`).

## What the three skills instruct

**Source-driven development** is a four-step loop: DETECT, FETCH, IMPLEMENT, CITE. The agent reads exact versions from the dependency file and states them in a `STACK DETECTED:` block. It fetches the specific doc page for the feature, not the homepage. Its source hierarchy puts the installed package (types, source, changelog) first, then official docs, then official blogs, web standards and compatibility tables. The skill says the installed package "is the final word on names and signatures for the version you will ship" (skill file, zizi-skills plugin). Code must match the docs, with no deprecated patterns. Docs-versus-codebase conflicts are raised as `CONFLICT DETECTED:` blocks at plan time. Citations with full URLs go in the PR body or conversation, never in code comments, and anything unverifiable is flagged `UNVERIFIED:`. The skill is skipped for version-independent edits or when the user wants speed. Public evidence supports the design. Expo's own agent index warns that AI models often give outdated Expo information ([Expo llms.txt](https://docs.expo.dev/llms.txt)), and Wake Mate's AGENTS.md already states the same rule. A study of deprecated API use covered 7 LLMs and 28,125 prompts ([arXiv 2406.09834](https://arxiv.org/pdf/2406.09834)). Documentation-augmented generation helps for rarely used APIs but can regress common ones unless retrieval is selective ([review of arXiv 2407.09726](https://www.themoonlight.io/review/on-mitigating-code-llm-hallucinations-with-api-documentation)). Both sources were read as summaries only.

**backend-design:design** is a command that wraps the six-step `think-before-coding` workflow, then hands the answers to a `component-architect` agent for a blueprint. No code is written until the user approves. The six steps and their outputs are:

| Step | Output |
|---|---|
| 1. Identify the context | Classification plus an expected load figure |
| 2. Model the data | Entities, schema-enforced invariants, ownership, lifecycle |
| 3. List failure modes | Detect, surface and recover decisions, plus a security pass |
| 4. Map authorization | Principal, scope, enforcement point ("anyone authenticated" is not an answer) |
| 5. Decide idempotence and concurrency | One sentence each for replay, concurrent and out-of-order runs |
| 6. Decide observability | Boundary logs, context-appropriate metrics, a definition of "healthy" |

Sibling skills add the test "what happens if this runs twice?", constraints in the schema rather than the app, definer functions that check ownership inside the body, and generic errors externally. The agent was not available in the research session, so the blueprint step was replaced by running the six answers directly against Wake Mate.

**zizi-skills:frontend** is a Vue 3 + Tabler web skill: "framework-agnostic in approach" but concrete only for web (skill file, zizi-skills plugin). Its transferable rules are these:
- Mirror the codebase.
- Build loading, empty and error states for every async surface; "the error branch is the one that gets forgotten".
- Do not block the whole view on one slow call.
- Treat "the page renders" as no evidence that a form is usable.
- Verify in light and dark, with inline screenshots.
- Run lint and typecheck.
- Never let a swallowed failure render a misleading empty state.

Tabler, PurgeCSS, SSR, vitest and the Vue reactivity traps do not apply. The skill has no mobile or Android content. Only `SKILL.md` was read, not its reference files.

## Source-driven development: the alarm rests on defaults nobody verified

Wake Mate matches the SDK 58 notification API where syntax is concerned. The handler fields `shouldShowBanner` and `shouldShowList` are current (`shouldShowAlert` is deprecated), and `DailyTriggerInput` with `channelId` inside the trigger is correct ([Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/)). The risk is behavioural. Per the installed types, `bestEffort` is the default and "some OEM Android builds defer these alarms by minutes", while `alarmClock` uses `setAlarmClock()` and is not deferred for battery optimization. Without the exact-alarm permission, `alarmClock` silently falls back to `bestEffort` (installed `Notifications.types.d.ts`; same behaviour documented on the SDK 58 page). The native delegate goes further: on API 31+ without `canScheduleExactAlarms()` it uses inexact `setAndAllowWhileIdle`. Wake Mate's `requestAlarmPermission()` asks only for POST_NOTIFICATIONS, so a wake-up alarm can slip with no warning to the user.

The permission declarations are the second finding. `app.json` declares both `SCHEDULE_EXACT_ALARM` and `USE_EXACT_ALARM`. Android says `USE_EXACT_ALARM` is granted on install and cannot be revoked, and that apps cannot publish with it "unless they qualify based on the policy language" ([Android 14 exact alarm changes](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms)). Expo's page says Play restricts it to alarm, timer and calendar app categories. Declaring both is the documented way to cover API 31-32 and 33+, but it triggers Play review. A sleep-matching alarm plausibly qualifies as an alarm clock app, but the actual Play policy text was never retrieved. Only secondary articles, which were not opened, say a restricted-permission declaration with a video is required. The `RECEIVE_BOOT_COMPLETED` entry is redundant, since Expo adds it automatically.

The remaining items are unverified API assumptions. `sound: 'default'` is passed at channel level, but the docs say to provide only a base filename. The Supabase client options (AsyncStorage, `autoRefreshToken`, `detectSessionInUrl: false`), the `EXPO_PUBLIC_SUPABASE_ANON_KEY` name, and the `getSession()` versus `getClaims` choice were not confirmed. Supabase does confirm that anonymous sign-ins strongly recommend invisible CAPTCHA or Turnstile and rate-limit by IP at 30 per hour ([Supabase anonymous sign-ins](https://supabase.com/docs/guides/auth/auth-anonymous)). Neither is reflected in the code.

Ranked changes, with the PR evidence the skill requires:

| # | Change | Why / evidence |
|---|---|---|
| 1 | Add `delivery: 'alarmClock'` to the DAILY trigger in `src/lib/alarm.ts`. | Documented for alarm clocks; avoids OEM deferral. Side effect: a status-bar alarm icon. |
| 2 | Call `getExactAlarmPermissionsAsync` and `requestExactAlarmPermissionsAsync`; explain the permission first; show an "alarm may be late" banner if denied. | Without the permission the alarm degrades silently to `bestEffort`. Re-check the exact API names on the SDK 58 page, which was truncated at 100k characters. |
| 3 | Decide between `USE_EXACT_ALARM` and `SCHEDULE_EXACT_ALARM` against the real Play policy text before release. | `USE_EXACT_ALARM` triggers Play review; the policy wording is unretrieved. |
| 4 | Verify the Supabase client options, key naming and `getSession` versus `getClaims`; wire CAPTCHA to `signInAnonymously`. | Supabase "strongly recommends" it; not implemented. |
| 5 | Verify `sound: 'default'`, content-level `priority`, `SafeAreaView`, and `DateTimePickerAndroid` usage against the SDK 58 and RN 0.88 docs. | All flagged UNVERIFIED. |
| 6 | Replace `cancelAllScheduledNotificationsAsync` with cancel-by-identifier. | Cancels every scheduled notification, not just the alarm; harmless today. |
| 7 | Add `docs/engine-reference/expo-notifications.md` pinning 58.1.8 with the verified signatures and a last-verified date. | The skill's own recommendation; the folder does not exist. |

The notes also say a notification is not a true alarm: no source read says it loops sound or overrides Do Not Disturb. That is a design question, taken up in the frontend section.

## Backend design: Wake Mate models a join, not a standing wake slot

The six-step review finds a sound core: UTC-slot rendezvous, a per-slot advisory lock, ownership checks inside each definer function, and deny-by-default RLS. In the original schema the `anon` role is denied (it is revoked from the functions), and direct inserts as `authenticated` fail. The root defect is that the model stores "a match row per join" rather than "a user's single standing slot". That one choice produces most of the faults below. Every "Tested" claim in this section comes from a scratch PostgreSQL 16.15 instance with a stubbed `auth` schema. It is not Supabase, so PostgREST, GoTrue, default grants and `auth.users` delete privileges are unproven.

Supabase's own guidance supports the hardening items. It says to prefer `security invoker`, set an empty `search_path` on definer functions, and warns that a definer function "can return rows the caller isn't allowed to read" ([Supabase: Database Functions](https://supabase.com/docs/guides/database/functions)). RLS guidance says to name the role and wrap `auth.uid()` as `(select auth.uid())` ([Supabase: Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)). Transaction-level advisory locks release at transaction end, which suits pooled connections ([PostgreSQL: Advisory Locks](https://www.postgresql.org/docs/current/explicit-locking.html)). `SKIP LOCKED` would not prevent same-user duplicate joins, because it only skips rows another transaction has already locked ([PostgreSQL: SELECT](https://www.postgresql.org/docs/current/sql-select.html)).

Ranked changes. The SQL for items 2 through 14 lives in `backend_design_patch_v2.sql`; item 1 is a sketch only.

| # | Impact | Defect (evidence) | Fix |
|---|---|---|---|
| 1 | High | `join_match` is called only from `enable()` in `index.tsx`, so the feature fires once per alarm change. A match covers one date, and DST shifts are never re-applied. | Short term: call the idempotent join on every foreground while the alarm is on. Long term: a server-side standing alarm plus a daily job. This is a design sketch, not run. |
| 2 | High | Pairing needs the identical UTC minute, so cold start nearly always yields a waiting row. | Quantise to 15-minute slots in `join_match` (tested: 07:14 and 07:01 paired). Later: batch pairing before the slot and an explicit solo state. |
| 3 | High | A user can sit in several slots. Tested on the original: join 420 then 360 gave two rows, and another user paired with the stale 07:00 slot. | Per-user lock, then slot locks in ascending order, then `private.detach_user` from every other future slot. Adds a `slot_at` column. |
| 4 | High | A paired user cannot leave: `leave_match` deletes only waiting rows, so the partner is stranded with a ghost. | `detach_user` promotes the partner to waiting and re-pairs. Without the merge step, the concurrency run left slots with two waiting rows; with it, 0 in 3 runs. |
| 5 | High | `block_and_report` leaves the live match untouched, although the UI promises no re-match. Reports are repeatable and unbounded. | Eject the reported user, re-pair the reporter, add a unique `(reporter, match_id)` index and a 500-character cap. Blocks keyed to anonymous UUIDs remain evadable by reinstalling. |
| 6 | High | `mark_awake` works 20 hours before the slot. | Enforce a window of slot minus 10 minutes to slot plus 3 hours. |
| 7 | Medium | Definer functions use `search_path = public`; the policy has no `to authenticated`; table grants are never revoked; each user receives the partner's UUID. | `search_path = ''`, revoke table grants, and return a narrow `match_view` (id, slot_at, paired, me_awake, mate_awake). This costs Realtime on `matches`; the app polls anyway. |
| 8 | Medium | No RPC rate limit. | A `private.rpc_calls` limiter raising `PT429` (the 21st join per hour was blocked). Per-user limits do not stop mass account creation. |
| 9 | Medium | Cascades delete the wrong rows: removing `user_b` deletes the whole match, and removing the reported user deletes the reports. | `user_b` becomes `on delete set null`, and the reports FKs are dropped. `user_a` still cascades. |
| 10 | Medium | Ghost partners: no cleanup of waiting rows, oldest-first selection. | Heartbeat via `last_seen` and pairing just before the slot; only the purge is tested. |
| 11 | Medium | No retention, and Supabase has no auto-cleanup of anonymous users. | `private.purge()` (14 days of matches, 180 days of reports, anonymous users inactive for 30 days by `last_seen`). Do not copy the docs' `created_at`-only filter, which would delete active users. |
| 12 to 14 | Low | Missing child-side indexes and `user_a <> user_b`; no lead time on the date boundary; `join_match(NULL)` raises a raw NOT NULL error. | Indexes and CHECK, a 5-minute lead time with `slot_at`-based ordering, and explicit error codes (`22023`, `28000`). |

A pgbench run of 16 clients over 3 runs of 320 joins showed no deadlocks, no user in more than one slot, no `user_a = user_b` row, and no slot with more than one waiting row. The lock order (user lock, then slot locks ascending, then rows) must be kept when extending the code. The client must change alongside the SQL: parse `match_view` in `match.ts`, handle `PT429` and `28000` instead of the three `.catch(() => undefined)` calls in `index.tsx`, and stop 5-second polling outside the wake window.

On safety, the pairing query honours blocks in both directions, and block/report exists in-app. That matches Google's requirement for in-app blocking on one-to-one features ([Google Play UGC policy](https://support.google.com/googleplay/android-developer/answer/9876937)). Google's child-safety page lists random-stranger and anonymous communication apps among those that must block minors ([Google Play Help 17036597](https://support.google.com/googleplay/android-developer/answer/17036597)). Wake Mate has no messaging, only an "awake" flag, so whether that category applies depends on a feature decision. The August 2026 effective dates come only from third-party articles. Wake Mate also keeps an indefinite per-user wake-time record. Whether that counts as personal data was not assessed.

## Frontend: tokens, semantics and honest states come before a native ringer

The skill's concrete content is web-only, so the audit used its universal gates plus Android sources. Equivalent gates for a dark-only RN app are dark mode at multiple font scales and display sizes, emulator screenshots, `npx expo lint` and `npx tsc --noEmit`. The highest-confidence defect is arithmetic: the "Turn alarm off" button sets `#14112b` text on `#3a3470`, about **1.66:1** (computed by the researcher with the WCAG formula). Android requires 4.5:1 for small text ([Android accessibility](https://developer.android.com/guide/topics/ui/accessibility/apps)). The same page recommends a 48dp touch target, and the bare "Block / report" text link falls below it at roughly one text line. The clock `Pressable` reads as concatenated text with no role, and nothing uses `role`, `accessibilityLabel` or `accessibilityState`, though React Native supports all three ([RN accessibility](https://reactnative.dev/docs/accessibility)). `SafeAreaView` is imported from `react-native`, which the docs mark "Deprecated. Use react-native-safe-area-context instead" ([reactnative.dev](https://reactnative.dev/docs/safeareaview)). That package is already installed, and edge-to-edge Android requires safe areas ([Expo system bars](https://docs.expo.dev/develop/user-interface/system-bars/)). The screen is not scrollable, so large font scales can push controls off-screen.

The state failures are the skill's own named failure mode. `refreshMatch`, `imUp` and `leaveMatch` swallow errors, so a failed join shows "Finding your mate…" forever and a failed "I'm up" looks like nothing happened. There is no hydration state before AsyncStorage loads, polling runs every 5 seconds regardless of AppState or failures, and `imUp` has no busy guard against double taps. Developer copy ("Copy .env.example") shows to end users. The product risk is larger: the "alarm" is a single notification sound with no loop, snooze or ringing screen, and tapping it only opens Home. A true ringing screen needs `USE_FULL_SCREEN_INTENT`, which Android 14+ grants only to calling and alarm apps ([AOSP FSI limits](https://source.android.com/docs/core/permissions/fsi-limits)). It also needs a native module or custom config plugin that the notes did not research.

| # | Change | Effort |
|---|---|---|
| 1 | Create `src/theme.ts`. Fix the ghost button: transparent background, 1px `#4a4390` outline, light text. Recheck every new colour pair. | Minutes |
| 2 | Accessibility pass: roles and labels, `accessibilityState` on disabled and busy buttons, `accessibilityLiveRegion="polite"` for mate status, a 48dp minimum on the report link, `maxFontSizeMultiplier` on the clock only, and non-announced emoji. | Hours |
| 3 | Switch to `react-native-safe-area-context` and wrap content in a `ScrollView`. | Hours |
| 4 | Add real states: a `hydrated` flag, an inline error banner with Retry, an offline note, an `actionError` in place of silent catches, and polling only while active and matched, with backoff. | A day |
| 5 | Split the 190-line `index.tsx` into `useAlarm` and `useMatch` hooks, components and a theme; validate stored JSON instead of `as SavedAlarm`. | A day |
| 6 | Ringing flow. Phase A, JS only: notification category with "I'm up" and "Snooze 5 min" actions, handled by `addNotificationResponseReceivedListener`, and a `/ring` route with back blocked. Phase B: native full-screen intent and looping audio. "I'm up" should be enabled only after the alarm rings, which matches the backend window. | Days to weeks |
| 7 | Smaller items: confirm before turning the alarm off, use the device 12/24h setting, show "next alarm", hide dev copy behind `__DEV__`, set a dark navigation theme, and darken the light adaptive-icon background. | Hours |

The frontend sketches were not compiled or run. Notification category and action option names, and `expo-network` for an offline indicator, need checking against the SDK 58 docs before use.

## What stays unverified

Verification is thin in four places. First, nothing ran on a device or emulator, so every frontend and alarm finding is static. Second, the backend tests ran on stock PostgreSQL with a stubbed `auth` schema; real Supabase behaviour, `pg_cron` availability, PostgREST mapping of `PTnnn` to HTTP status, and the right to delete from `auth.users` are all unchecked. Third, the Google Play text for `USE_EXACT_ALARM`, `USE_FULL_SCREEN_INTENT` and the anonymous-chat categories was not retrieved from Google; the dates and the exact-alarm requirements rest on secondary articles. Fourth, the last roughly 24k characters of the Expo notifications page, the Supabase React Native client options, the `@react-native-community/datetimepicker` and RN 0.88 docs, and `src/lib/match.ts` beyond usage were not read. The academic evidence on LLM API drift comes from search summaries, and WebFetch output is itself a model summary that should be re-checked against live URLs before quoting in a PR. No load figure exists, no Play Integrity or legal analysis was done, and the `component-architect` agent step did not run.

## Conclusion

The three skills converge on one gap. Wake Mate's code is plausible where a reviewer would look, but its guarantees rest on defaults: a best-effort alarm, a join-per-change model, and swallowed errors that look like empty states. Source verification finds the alarm default, schema design finds the missing lifecycle, and the frontend gates find the hidden failures. Together they imply a build order: ship the cheap certain fixes first (`delivery: 'alarmClock'`, the contrast tokens, the accessibility and safe-area pass, the error states, and a foreground re-join). Next, apply the backend patch with matching client changes, moving schema changes into migrations since `schema.sql` is run by hand today. The native ringer and the Play policy review belong to a separate track, because they decide whether Wake Mate can honestly call itself an alarm.
