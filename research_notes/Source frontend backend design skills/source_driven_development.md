# Source-driven development skill, and applying it to Wake Mate (Expo SDK 58, Android)

Scope note: research date 2026-11-08. Wake Mate versions come from package.json: expo ~58.0.23, expo-notifications ~58.1.8 (installed 58.1.8), react-native 0.88.1, react 19.3.0, @supabase/supabase-js ^2.119.0. Local file paths are under /home/user/Personal-Projects/wake-mate.

## 1. What does the source-driven-development skill instruct an agent to do?

### Takeaway
The skill is a four-step loop (DETECT, FETCH, IMPLEMENT, CITE). The agent reads exact versions from the dependency file, fetches the specific official doc page (or the installed package's own types and source) for the feature, writes code that matches that doc, and cites full URLs in the PR body or conversation. Anything it cannot verify must be flagged UNVERIFIED. It applies to framework-specific code where version matters and is skipped for version-independent edits or when the user wants speed.

### Cited Findings
Source for all items in this section: the skill file, /root/.claude/plugins/synced/f69a9f57-eaea-4da2-896d-07c7681a5ac0_b37344c7-d43a-4ccd-837a-bab3456b4bb6/11922719-c2b0-4b58-9751-2dd37b3f91f9/skills/source-driven-development/SKILL.md (local file, name `source-driven-development`, category Engineering; shipped in the zizi-skills plugin).
- Core rule: "Every framework-specific code decision must be backed by official documentation. Don't implement from memory — verify, cite, and let the user see your sources."
- When to use: user wants current best practices; boilerplate or patterns that will be copied across a project; user asks for "documented, verified, or 'correct'" implementation; features where the framework's recommended approach matters (forms, routing, data fetching, state management, auth); reviewing framework-specific code; "Any time you are about to write framework-specific code from memory."
- When NOT to use: correctness does not depend on version (renames, typos, moving files); pure logic (loops, conditionals, data structures); the user "explicitly wants speed over verification."
- Step 1 Detect: read the dependency file and state the stack explicitly in a `STACK DETECTED:` block with versions. "If versions are missing or ambiguous, ask the user. Don't guess — the version determines which patterns are correct."
- Step 2 Fetch: fetch "the specific documentation page for the feature you're implementing. Not the homepage, not the full docs." Source hierarchy: 0 = the installed package itself at the pinned version (node_modules sources, .d.ts, CHANGELOG, vendor/, site-packages/); 1 = official documentation; 2 = official blog/changelog; 3 = web standards (MDN, web.dev); 4 = compatibility tables (caniuse, node.green). Quote: "The installed package is the final word on names and signatures for the version you will ship: docs track the latest release, and a version newer than your training is exactly where memory fails. Read its types or source first, then the docs for how to use it."
- Keep what you verified: for pins newer than model training, keep a per-library note in `docs/engine-reference/<library>.md` with pinned version, verified signatures of APIs actually called, a "don't use X, use Y" list, sources, and a "last verified" date; read it before the docs, update it in the same change that bumps the pin; "anything in it that disagrees with the installed package loses."
- Conflicting official sources (e.g. migration guide vs API reference): surface to the user and verify which works against the detected version.
- Step 3 Implement: use signatures from docs, not memory; use the new way if docs show one; do not use deprecated patterns; "If the docs don't cover something, flag it as unverified." Docs-vs-codebase conflicts get a `CONFLICT DETECTED:` block with options A/B, raised "at plan time, in the single batched question round, not mid-implementation."
- Step 4 Cite: every framework-specific pattern gets a citation, but "in the PR body / conversation, never in committed code comments." Rules: full URLs (no shorteners); prefer deep links with anchors; quote the passage for non-obvious decisions; include runtime/browser support data for platform features; if no docs found, emit `UNVERIFIED: I could not find official documentation for this pattern. This is based on training data and may be outdated. Verify before using in production.` and "Honesty about what you couldn't verify is more valuable than false confidence."
- Verification checklist (8 items): versions identified from dependency file; official docs fetched; all sources official (not blogs/training data); code matches current-version docs; non-trivial decisions cited with full URLs outside code comments; no deprecated APIs (checked against migration guides); conflicts surfaced at plan time; unverifiable items flagged.
- Related skills: planning (conflicts raised in the question round) and debugging-and-error-recovery (same verify-against-source rule applied to failures).

### Inferences
- The skill's step 0 (read the installed package) is the highest-value step for Wake Mate: expo-notifications 58.1.8 is in node_modules with its Kotlin sources, and those answered questions the web docs page did not (see section 3).
- The skill's rule against citation comments means Wake Mate's code should stay uncluttered and the evidence should live in a PR description or an optional docs/engine-reference/expo-notifications.md note. That docs/ directory does not exist today (checked).

### Gaps
- The skill does not say how to handle a docs page that is partially unreadable or very large (the Expo notifications page exceeded 100k characters); I had to read the rest from node_modules.

## 2. Why does docs-grounded coding matter for fast-moving frameworks like Expo? (public evidence)

### Takeaway
Research on LLM code generation consistently shows deprecated or version-mismatched API usage, and that putting documentation into context improves API-call accuracy, though selectively. Expo itself tells agents not to trust training data and publishes machine-readable versioned docs, and Wake Mate's own AGENTS.md repeats that rule.

### Cited Findings
- Expo's own agent-facing index says AI models often give outdated Expo information; examples of stale knowledge: "`expo eject` command was removed in SDK 46 (2022)", the managed/bare distinction is outdated, global `expo-cli` is deprecated. It says any page can be fetched as markdown with an `Accept: text/markdown` header or by appending `.md`, points agents to https://docs.expo.dev/agents.md, and lists `versions/latest/...` paths — [Expo llms.txt](https://docs.expo.dev/llms.txt). (My fetch summary did not show how to target a specific SDK version via URL beyond `latest`; the Wake Mate AGENTS.md says `https://docs.expo.dev/versions/v<major>.0.0/`, and that URL pattern worked for me: `.../versions/v58.0.0/sdk/notifications/`.)
- Wake Mate's own AGENTS.md states: "Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed" and instructs reading the major version of `expo` and fetching matching versioned docs — local file /home/user/Personal-Projects/wake-mate/AGENTS.md. This is essentially the skill's DETECT and FETCH steps written as a project rule.
- A study of deprecated API usage in LLM code completion covered 7 LLMs, 145 API mappings across 8 Python libraries, and 28,125 prompts — [arXiv 2406.09834](https://arxiv.org/pdf/2406.09834). (I only read a search summary, not the full paper.)
- Library-hallucination analysis: asking for libraries "from" a given year increased hallucinations, with more recent years higher; none of the hallucinated responses included version numbers — [arXiv 2509.22202](https://arxiv.org/pdf/2509.22202) (via search summary).
- CloudAPIBench / Documentation Augmented Generation: adding docs helps for low-frequency APIs but can regress high-frequency ones unless retrieval is selective — [review of arXiv 2407.09726](https://www.themoonlight.io/review/on-mitigating-code-llm-hallucinations-with-api-documentation) (secondary summary).
- Secondary or weak sources, treat with caution: LibEvoBench summary reporting docs in prompts raised API-call accuracy 10-20 points while explicit version tags alone did not help — [Emergent Mind](https://www.emergentmind.com/papers/2606.25402) (not verified against the paper); a blog citing 25-38% deprecated-API rates across seven LLMs — [Tian Pan](https://tianpan.co/blog/2026/06/01/the-library-version-your-coding-agent-remembers-wrong) (author notes it could not be checked against the paper); an undergraduate thesis claiming up to 60% lower hallucination with official docs — [SCU](https://scholarcommons.scu.edu/cseng_senior/319).

### Inferences
- The combined evidence supports the skill's design: put the version-matched doc (or the installed source) in context, rather than just naming a version in the prompt. The selective-retrieval caveat matches the skill's "fetch the specific page, not the full docs" rule.
- Wake Mate is a good example of drift risk: expo-notifications 58.x has a `delivery: 'alarmClock'` trigger option, `shouldShowBanner/shouldShowList` handler fields, and `requestExactAlarmPermissionsAsync`, all of which differ from older SDK memory (e.g., `shouldShowAlert`, now deprecated per the SDK 58 docs below).

### Gaps
- I could not retrieve the full text of the academic papers (only search summaries), and found no Expo-specific quantitative study of LLM error rates. Numbers above are from summaries, not primary reading.

## 3. Which Wake Mate code rests on API assumptions to verify, and what do the docs say?

### Takeaway
The code largely matches SDK 58 notification APIs (handler fields, channel, DAILY trigger, channelId inside the trigger). The material risks are in alarm reliability and Play policy, not syntax: the DAILY trigger defaults to `delivery: 'bestEffort'` rather than `setAlarmClock`, the app never requests or checks exact-alarm permission, it declares both SCHEDULE_EXACT_ALARM and USE_EXACT_ALARM (the latter is Play-policy restricted), and the app plays a notification sound rather than a true ringing alarm. Several Supabase and notification details I could not confirm from official pages.

### Cited Findings

#### src/lib/alarm.ts
- Handler fields `shouldShowBanner`, `shouldShowList`, `shouldPlaySound`, `shouldSetBadge` are the current ones; `shouldShowAlert` is deprecated ("instead, specify shouldShowBanner and / or shouldShowList") — [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/). Wake Mate uses the current fields (alarm.ts lines 6-13). Verified.
- Trigger type: `DailyTriggerInput` with `hour`, `minute`, optional `channelId`; `SchedulableTriggerInputTypes.DAILY` — [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/). Wake Mate puts `channelId` inside the trigger (correct for Android; the docs example does the same) and calls `setupAlarmChannel()` first. Verified.
- Channel behavior: after a channel is created "you can modify only its name and description. This limitation is imposed by the Android OS" — [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/). Implication: `ALARM_CHANNEL = 'wake-alarm'` with importance MAX, vibration and sound is permanent per install; a later change to importance/sound needs a new channel id. `AndroidImportance.MAX` is used in the docs' own Snack example.
- Sound: docs say `sound` takes a base filename ("Provide ONLY the base filename") — [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/). Wake Mate passes `sound: 'default'` in both the channel and the content. I did not find a passage in the part of the page I read confirming `'default'` as a channel-level value. UNVERIFIED.
- Exact timing, from the installed package types (node_modules/expo-notifications/build/Notifications.types.d.ts lines ~125-145): "`'bestEffort'`: the default. Uses `setExactAndAllowWhileIdle()` ... Some OEM Android builds defer these alarms by minutes... Without the exact alarm permission, the system may deliver the notification later than requested. `'alarmClock'`: uses `setAlarmClock()`. The system delivers these alarms at the requested time and does not defer them for battery optimization. Use only for time-critical alarms, such as alarm clocks or medication reminders. The status bar shows an alarm icon until the notification is delivered. Requires the `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM` permission on Android 12 and higher. Without the permission, the notification is scheduled as `'bestEffort'`." Wake Mate's trigger omits `delivery`, so it gets `bestEffort`. The SDK 58 docs page agrees that `delivery` is optional with default `'bestEffort'`, and that without the permission "scheduled notifications arrive at an approximate time, and `delivery: 'alarmClock'` falls back to `'bestEffort'`" — [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/).
- Native implementation (installed source, android/src/main/java/expo/modules/notifications/service/delegates/ExpoSchedulingDelegate.kt, `setupAlarm`): if API >= 31 and `canScheduleExactAlarms()` is false it uses `setAndAllowWhileIdle` (inexact, can slip); else if alarmClock it uses `setAlarmClock`; else `setExactAndAllowWhileIdle`. The code comment reads "setAlarmClock() alarms are never adjusted by the system. OEM battery policies defer setExactAndAllowWhileIdle() alarms by minutes on some devices but leave these alone." Local source, not web docs.
- Expo exposes `getExactAlarmPermissionsAsync` / `requestExactAlarmPermissionsAsync` (installed source: NotificationPermissionsModule.kt). `requestExactAlarmPermissionsAsync` resolves immediately if exact alarms are already allowed (or API < 31); otherwise it throws `ExactAlarmPermissionNotDeclaredException` unless SCHEDULE_EXACT_ALARM is declared in the manifest, and otherwise opens `ACTION_REQUEST_SCHEDULE_EXACT_ALARM`. Wake Mate's `requestAlarmPermission()` calls only `getPermissionsAsync`/`requestPermissionsAsync` (POST_NOTIFICATIONS) and never calls the exact-alarm functions. I have not read the SDK 58 doc page's entries for these two functions (page was truncated at 100k characters), so the exact documented API names should be re-checked on the page.
- `priority: AndroidNotificationPriority.MAX` in content: exists in the installed types (Notifications.types.d.ts line ~516, `priority?: AndroidNotificationPriority`, "Relative priority for this notification..."). The web fetch could not confirm the content-level field. On Android 8+ the channel's importance governs heads-up behaviour (Android platform behaviour from general knowledge; not fetched here, UNVERIFIED in this session).
- `cancelAllScheduledNotificationsAsync()` is called both before scheduling and in `cancelAlarm()`. This also cancels any other scheduled notification; fine today since the app schedules only the alarm. Native code confirms it cancels the AlarmManager entries (ExpoSchedulingDelegate.removeAllScheduledNotifications).
- Reboot: the docs say RECEIVE_BOOT_COMPLETED "is added automatically" because the module needs it "to set up scheduled notifications when the device (re)starts" — [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/). Android's own docs say "By default, all alarms are canceled when a device shuts down" and boot receivers must reschedule — [Android: Schedule alarms](https://developer.android.com/develop/background-work/services/alarms/schedule). So the `RECEIVE_BOOT_COMPLETED` entry in app.json is redundant per Expo docs (harmless).
- Doze: Android says "Alarms don't fire when the device is in Doze mode. Any scheduled alarms are deferred until the device exits Doze", and an exact alarm is one option when work must run — [Android: Schedule alarms](https://developer.android.com/develop/background-work/services/alarms/schedule).
- `localToUtcMinute` uses today's UTC offset (DST changes could shift the user's UTC minute later; pure JS logic, not framework-specific, so outside the skill's scope).

#### app.json
- Android 12+: SCHEDULE_EXACT_ALARM is needed to schedule exact alarms; Android 14+ denies it by default for newly installed apps; on Android 13+ alarm clock, timer and calendar apps can declare USE_EXACT_ALARM, which is granted without a prompt; Google Play "restricts `USE_EXACT_ALARM` to those app categories" — [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/).
- Android developer docs: "`SCHEDULE_EXACT_ALARM` ... is no longer being pre-granted to most newly installed apps targeting Android 13 and higher"; "Calendar or alarm clock apps need to send calendar reminders, wake-up alarms... These apps can request the `USE_EXACT_ALARM` normal permission. The `USE_EXACT_ALARM` permission will be granted on install"; "Apps will not be able to publish a version of their app with this permission in the manifest unless they qualify based on the policy language" — [Android 14 exact alarm changes](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms).
- Android guidance on choosing between the two: "Your app should use exact alarms, and declare either `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM` permission, only if a user-facing function in your app requires precisely-timed actions." USE_EXACT_ALARM: granted automatically, cannot be revoked by the user, subject to Play policy, limited use cases. SCHEDULE_EXACT_ALARM: granted by the user, broader use cases; "When the `SCHEDULE_EXACT_ALARM` permission is revoked for your app, your app stops, and all future exact alarms are canceled." — [Android: Schedule alarms](https://developer.android.com/develop/background-work/services/alarms/schedule).
- Android also says "If your app's core functionality depends on a precisely-timed alarm — such as for an alarm clock app or a calendar app — then it's OK to use an exact alarm", and "all repeating alarms are inexact alarms" for the AlarmManager repeating APIs — [Android: Schedule alarms](https://developer.android.com/develop/background-work/services/alarms/schedule). (Expo's DAILY trigger, per installed source, schedules individual alarms with setExactAndAllowWhileIdle/setAlarmClock rather than the platform repeating API; I read `setupAlarm` but not how it re-arms after firing.)
- Wake Mate's app.json declares POST_NOTIFICATIONS, SCHEDULE_EXACT_ALARM, USE_EXACT_ALARM, VIBRATE, RECEIVE_BOOT_COMPLETED (local file). The Expo config plugin for expo-notifications (plugin/build) contains no references to the exact-alarm permissions (grep returned nothing), so these two permissions come only from app.json. Declaring both is the Android-documented pattern for covering API 31-32 (where USE_EXACT_ALARM does not exist) plus 33+, but Play policy review is triggered by USE_EXACT_ALARM.
- Exact Play policy text: not retrieved. The Play Help policy page I fetched (support.google.com/googleplay/android-developer/answer/12253906) returned only a deadlines list; Android's docs link to its "exact_alarm_preview" section. Secondary sources (not authoritative) say the policy limits the permission to alarm clock and calendar apps, requires the Play Console restricted-permissions declaration with a video, and that automated review can block the release — [Medium/Gravel Engineering](https://medium.com/gravel-engineering/exact-alarm-permission-google-plays-ticking-time-bomb-for-android-developers-e29e4d20b572) and [Esper](https://www.esper.io/blog/android-13-exact-alarm-api-restrictions) as surfaced by search; I did not open them.
- Recommended best practice from Android: call `canScheduleExactAlarms()` before scheduling, send the user to `ACTION_REQUEST_SCHEDULE_EXACT_ALARM` if not granted, listen for `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`, and "gracefully degrade" if denied — [Android 14 exact alarm changes](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms). Expo's native module implements the check internally and falls back to `setAndAllowWhileIdle`.
- Expo docs on revocation: "If the user revokes the permission in settings, Android restarts the app and the request promise never resolves" — [Expo SDK 58 Notifications](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/).
